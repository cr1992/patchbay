## 动机

实测复现见 [目标面遮挡语义复现](../verification/0.5.0-target-plane-occlusion-repro.md) 发现 2：目标已挂载但被不透明浮层遮挡时，`ui reveal` 与目标压根不存在（含 identifier 拼错）时返回同一个 `uiRevealNoScrollableContainer`（`reveal/reveal_bridge.dart` 的 `_admit` 在 candidates 为空时对两种情况走同一拒绝分支），而同一时刻语义面对同一目标已经能报 `uiSemanticsTargetObscured`；真实业务里 modal 场景远比「目标不在列表里」常见，现有码把调用方引导去查滚动容器和 `--container`，误导成本集中在排障时间上

## 备注

方向：目标 mounted 且 obscured 时给独立拒绝形态（例如 `uiRevealTargetObscured`，或至少在 `uiRevealNoScrollableContainer` 的 details 里带 `obscured: true` 与语义面同款 `reason`），`reveal_engine.dart:529` 已在读 `data.flagsCollection.isObscured` 构造目标，事实在引擎内可得；新增稳定 code 需过 `packages/patchbay/test/error_code_registry_ratchet_test.dart` 的封闭注册表与相应 Proposal/裁决，附带解决同一码下「identifier 拼错」与「不在可滚容器里」的合并问题
