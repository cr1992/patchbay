## 这份证据要回答什么

[PB-050-36](../backlog.d/PB-050-36.md) 的起点是一次真机观察，碎片自己写明「单设备单接入方，尚未定性」：
目标已曝光时传入越过 `revealPolicy` 上限、仍在命令参数域 `1..200` 内的 `--max-steps`，静默返回
`revealed` / `steps: 0` / 退出 0，观察不到 `uiRevealBudgetExceeded`。

Proposal 要求在裁决前确认两件事，并明确「不得先按直觉改顺序」：

1. **有可驱动容器时 `_run` 是否可达、预算门是否如期拒绝**；
2. **缺口是否仅限无容器的短路路径**。

两条都已确认。结论：**预算门实现是好的，缺口在它被求值的位置**。

## 载体：widget 表征测试，而非一次设备会话

复现落在 `packages/patchbay_flutter/test/reveal/reveal_budget_order_test.dart`，5 个用例。

选这个载体的理由是「决定性」这个词本身：待答的是 `reveal_bridge.dart` 内部的**求值顺序**，
而 widget 测试带真实 `Scrollable` 与真实 `SemanticsOwner`，能把三条终止路径用同一份越界参数并列跑出来，
且在 CI 上可无限次重复。原始真机观察之所以「尚未定性」，恰恰因为它是单次、单设备、无对照的。

**这不替代设备验收**，见下文「未证明范围」。`example_reveal_screen.dart` 已具备浮层与滚动容器两半，
若仍需一次设备会话确认，增量很小。

## 三方对照

同一份越界参数（policy `maxSteps: 2` / `maxDurationMs: 1000`，调用 `maxSteps: 40` / `timeoutMs: 5000`），
分别落在三条终止路径上：

| 场景 | 终止路径 | 预算门 | 实际结果 |
|---|---|---|---|
| 有可驱动容器 + 目标屏外 | `_run` 可达 | **求值** | `uiRevealBudgetExceeded`，`exceeded: [maxSteps, timeoutMs]`，`ScrollController.offset` 仍为 0 |
| 无可驱动候选 + 目标已露出 | `_admit` 短路成功 | **未求值** | `revealed` / `steps: 0` / 无 rejection |
| 无可驱动候选 + 目标未露出 | `_admit` 短路拒绝 | **未求值** | `uiRevealNoScrollableContainer`，details 不含 `exceeded` |

源码定位与碎片记载一致：参数域校验只比 host 硬顶 `1..200`
（`packages/patchbay_flutter/lib/src/reveal/reveal_bridge.dart:70-87`）；policy 上限比对在
`_decisionRejection:343-362`，而它只由 `_run:183` 调用，`_run` 只在 `_admit:124` 返回 anchor 后才到达；
`_admit` 在可驱动候选为空且目标已露出时短路成功（`:387-391`）、为空且未露出时拒
`uiRevealNoScrollableContainer`（`:392-401`）——两条终止路径都不评估 policy 预算。

## 已排除：不是字段级遗漏

若只有 `maxSteps` 被吞、`timeoutMs` 仍生效，缺口就是字段级遗漏而非求值位置问题，裁决方向随之不同。
逐字段各验一次（`maxSteps` 越界 / `timeoutMs` 越界，另一项合法）：**两者都被已露出短路吞掉**。
因此这是单一的求值位置问题，一处顺序决策即可覆盖。

## 结构性约束：policy 上限是**按容器**授权的，短路路径上没有容器可问

尝试把预算门前置到 `_admit` 之前做原型量测时，改动**编译不过**，而失败原因本身是裁决输入：

```
error • The argument type 'SemanticsNode?' can't be assigned to the parameter type
'PatchbaySemanticsTarget'. • lib/src/reveal/reveal_bridge.dart:128
```

`PatchbayRevealPolicy` 的入参不是目标而是**容器**（`reveal_models.dart:103-107`，参数名即
`container`），并且源码注释已把理由写定：「入参是容器而不是目标：reveal 的核心场景里目标根本不存在，
唯一存在的、也是真正被移动的东西是容器」。policy 只在 `_run:182` 与步间重评 `:219` 被调用，两处都传
已准入的容器锚点。

因此两条 `_admit` 短路路径上**不存在可传给 policy 的容器**，也就无从取得 policy 的 `maxSteps` 上限。
这意味着「policy 上限作为所有调用的前置参数门」不是把一次调用往前挪，而是二者之一：

- 改 `PatchbayRevealPolicy` 签名以接受"没有容器"这一情形——接入方 breaking，且与该 typedef 现有
  设计立场直接冲突；
- 另立一个与容器无关的预算上限，与按容器授权的 policy 并存——即新增一层预算。

同时值得注意：与容器无关的调用级上限**已经存在且已在最前面执行**——host 硬顶 `1..200` /
`1..120000` 就在 `reveal_bridge.dart:70-87` 求值，越界即拒，与是否有容器无关。

本文件不替 DG-060-05 做裁决，只把这条约束摆出来：现状的分层是「调用级硬顶前置求值，容器级 policy
预算在容器真正被驱动时求值」，而观察到的"静默成功"落在这个分层的必然结果上，而不是落在一次顺序疏漏上。

## 证明范围

- 有可驱动容器时 `_run` 可达，预算门按预期逐项拒绝，且拒绝前不发生任何滚动派发。
- 两条 `_admit` 短路路径都完全不评估 policy 预算，`maxSteps` 与 `timeoutMs` 同时被吞。
- 缺口范围就是这两条短路路径，不涉及预算门自身实现。
- 三条路径均未派发 `showOnScreen`（沿用既有 `ShowOnScreenRecorder` 断言）。

## 给 DG-060-05 的裁决输入

Proposal 的待裁决项是「policy 上限是所有调用的前置参数门，还是只在滚动执行路径求值」。两个方向的义务
现在都可具体化：

- **裁「前置参数门」**（改顺序）：不是移动一次调用。受上文结构性约束限制，它要么改
  `PatchbayRevealPolicy` 签名以表达"没有容器"（接入方 breaking，且与该 typedef 的现有设计立场冲突），
  要么另立一层与容器无关的预算上限。此外这是**行为变化**：今天返回 `revealed` / 退出 0 的调用会开始
  拒绝，需迁移说明与老 reader 口径；本文件对应的两条表征断言要改成契约断言。
- **裁「仅约束滚动执行预算」**（保持现状）：把当前分层写进 `ui.reveal` 的 help 与 descriptor 语义——
  调用级硬顶前置求值、容器级 policy 预算在容器真正被驱动时求值，越界参数在短路路径上不构成拒绝。
  零行为变化、零接入方改动，本文件的断言原样转为契约断言。

第三种可能也值得摆出来：接入方最初的预期偏差是「越界即 budgetExceeded」，而现状下越界参数在短路路径上
连 policy 都没被问到。若裁决保持现状，help 的措辞需要明确区分**调用级硬顶**与**容器级 policy 预算**
这两层，否则同样的误读会再次发生——这也是 PB-050-36 从一次真机观察变成一条台账的原因。

无论哪个方向，`exceeded` 逐项列出与「拒绝前不滚动」这两点都已被覆盖，不需要重新取证。
