## 发现 1：注册文本目标面（`ui.text.*`）没有遮挡概念

### 现象一句话

同一个浮层盖住同一块区域时，语义面的 `ui tap` 按 `uiSemanticsTargetObscured` 拒绝，而注册目标面
的 `ui text set` 返回 `applied` 且**文字确实写进了输入框**——自动化能往一个真人绝对点不到、也输入
不了的字段里写值。

### 最小结构

在一个注册文本目标上面盖一层参与命中测试的不透明浮层：

```dart
// 目标：一个已注册的文本目标（沿用 example 既有的 PatchbayKey.text）
final PatchbayKey noteKey = PatchbayKey.text(
  noteTargetId,                       // 'example.note'
  operationGates: const <PatchbayUiOperation, Set<String>>{
    PatchbayUiOperation.textSet: <String>{exampleWriteGate},
    PatchbayUiOperation.textEnter: <String>{exampleWriteGate},
  },
  registry: registry,
);

// 屏：输入框在下，浮层在上，浮层完全覆盖输入框的矩形
Stack(
  children: <Widget>[
    Center(
      child: TextField(key: noteKey, controller: controller),
    ),
    // 与 example_reveal_screen.dart 的 pinned bar 同形状：不透明、参与命中测试
    Positioned.fill(
      child: Listener(
        behavior: HitTestBehavior.opaque,
        child: Semantics(
          identifier: 'repro.blocker',
          label: 'blocker',
          child: ColoredBox(color: Theme.of(context).colorScheme.inverseSurface),
        ),
      ),
    ),
  ],
)
```

等价形态：任何 `showDialog` / `ModalRoute` 带出来的 `ModalBarrier`，或任何 `AbsorbPointer` 包住的
整屏浮层。接入方现场用的是一个业务浮层，形状与上面一致。

### 命令序列

```bash
# 0) 确认浮层已挂载、目标在浮层下方
patchbay ui semantics tree --output tree.json --force --max-inline-bytes 0

# 1) 语义面：对被浮层盖住的、带 tap 的目标发 tap
patchbay ui tap <被盖住的 semantics identifier> --json

# 2) 注册目标面：对被同一浮层盖住的注册文本目标写值
patchbay ui text set example.note <generation> "written-through-overlay" --json

# 3) 回读：截图或读输入框的值，确认第 2 步是否真的落了字
patchbay capture root --output after.png --force --pixel-ratio 1.0
```

### 期望 vs 实际

| 步骤 | 期望 | 实际 |
|---|---|---|
| 1 | 拒绝 | ✅ 拒绝：`uiSemanticsTargetObscured`，`details.reason = "hitTestOrClip"`，并指名 `nodeId` / `generation` / `identifier` |
| 2 | （待裁决）拒绝，或明确声明本面不查遮挡 | ❌ `admission: accepted`，`payload.outcome: "applied"`，无 notice、无 rejection |
| 3 | —— | ❌ 字确实写进去了（截图可见） |

### 源码定位（仓内路径）

`obscured` 在 `packages/patchbay_flutter/lib/` 下只出现在四个文件：

- `lib/src/semantics/semantics_models.dart:55,64,73,80`（`PatchbaySemanticsTarget.obscured` 等）
- `lib/src/semantics/semantics_bridge.dart:166,379,426,446-456,609,613,853,867-868,911`（含
  `patchbaySampledOcclusionReason(...)` → `'reason'`）
- `lib/src/reveal/reveal_engine.dart:529`
- `lib/src/ui_wait_bridge.dart:146`

文本路径不在其中。`ui.text.set` / `ui.text.enter` 的链路是：

```
lib/src/flutter_service_host.dart:331  → bridge.setText(...)
lib/src/flutter_service_host.dart:343  → bridge.enterText(...)
lib/src/flutter_bridge.dart:381        setText()   ─┐
lib/src/flutter_bridge.dart:396        enterText() ─┴→ _applyText(...)
```

`_applyText` 依次做的检查是：`_registry._resolve(id, generation:)`（挂载 / generation / 歧义）→
`_gates.evaluate(declaration.gatesFor(operation))` → gate 可能 await，**再解析一次**防止旧
generation 拿到续跑。全程**没有任何一步查遮挡**。

对应地，注册目标描述符（`PatchbayUiTargetDescriptor`，`catalog()` 回报的那个）只有 `mounted` /
`ambiguous` / `operations` / `operationGates` / `sensitivePolicy` / `sideEffect` 等字段，**没有
`obscured`**；而语义面的 `PatchbaySemanticsTarget` 有。所以这是结构性的，不是某一处漏判。

### 说明与待裁决点

- **这不是 0.5.0 回归**：`ui.text.*` 与注册目标面在 0.4.x 就是这个形状，本轮只是被真机验收顺带
  照出来。
- 待裁决的是取哪一种：
  1. 注册目标面**本就是接入方显式声明的自动化面**，与「装成用户去点」的语义面不同档，不查遮挡
     是有意设计——那么建议在 `ui.text.*` 的命令文档里写明这条边界，避免调用方从「遮挡拒绝」推广
     到整个 `ui.*`；
  2. 或者它应当与语义面对齐——那么需要给注册目标补一个遮挡判定，并考虑 `uiTargetObscured` 之类
     的码。
- 无论取哪种，接入方侧的实际影响是：**不能用 `ui text set` 的成功来推断"这个字段此刻对用户可用
  "**。写自动化脚本时如果拿 text 写入当作"页面已就绪"的判据，会在有 modal 的路径上静默走偏。

## 发现 2：`ui.reveal` 分不清「被浮层遮挡」与「不在可滚容器里」

### 现象一句话

目标**已挂载但被浮层盖住**，和目标**根本不在任何可滚容器里**（含 identifier 拼错），`ui reveal`
返回同一个 `uiRevealNoScrollableContainer`。前者的真实原因是有个 modal 盖着，而拒绝文案把调用方
引向"去查滚动容器"。

### 最小结构

复用发现 1 的那一屏即可，只把被盖的目标换成一个带 `Semantics(identifier: ...)` 的普通可点节点
（不必是文本目标），并确保它**不在**任何 `Scrollable` 内：

```dart
Stack(
  children: <Widget>[
    Center(
      child: Semantics(
        identifier: 'repro.target',
        button: true,
        onTap: () {},
        child: const ExcludeSemantics(child: Text('target')),
      ),
    ),
    Positioned.fill(
      child: Listener(
        behavior: HitTestBehavior.opaque,
        child: Semantics(
          identifier: 'repro.blocker',
          label: 'blocker',
          child: ColoredBox(color: Theme.of(context).colorScheme.inverseSurface),
        ),
      ),
    ),
  ],
)
```

前提：接入方已注入 `revealPolicy`（否则 `ui.reveal` 不进 catalog，见文末附录第 3 条）。

### 命令序列与对照

```bash
# 场景 A：目标已挂载，但被不透明浮层完全盖住
patchbay ui reveal repro.target --json

# 场景 B：目标压根不存在（等价于 identifier 拼错）
patchbay ui reveal repro.no.such.target --json

# 对照：同一时刻语义面对场景 A 的目标怎么说
patchbay ui tap repro.target --json
```

| 场景 | 真实原因 | 实际返回 |
|---|---|---|
| A | 被浮层遮挡 | `uiRevealNoScrollableContainer`，notice「No drivable scroll container encloses the target.」 |
| B | 目标不存在 / 拼错 | `uiRevealNoScrollableContainer`，notice「No drivable scroll container is mounted.」 |
| 对照 | 同一目标、同一时刻 | `uiSemanticsTargetObscured` + `reason: "hitTestOrClip"` ——**语义面知道它被盖住了** |

也就是说，遮挡这个事实在同一进程、同一帧里是**已知的**（语义面刚报过），reveal 却没有用它来解释
自己的失败。

补充一个次要观察：显式 `--container <非滚动锚点>` 也落在同一个码上，notice 是「The container
anchor encloses no scroll node that currently exposes a same-axis scroll action.」——这一条的
文案是准确的，问题只在前两种。

### 为什么值得区分

真实业务屏上「目标被 modal / bottom sheet / 全屏 loading 盖住」远比「目标不在列表里」常见。照
0.5.0 文档的 `reveal → 按 reachability 分流 → act` 循环写自动化的人，拿到
`uiRevealNoScrollableContainer` 的第一反应会是去查滚动容器和 `--container` 参数，而真正该做的是
先把浮层关掉。误导成本集中在排障时间上。

### 建议方向（供参考，不是结论）

目标已挂载、`obscured == true` 且没有可驱动容器时，给一条与语义面同族的码（例如
`uiRevealTargetObscured`），或至少在现有码的 `details` 里带上 `obscured: true` 与语义面同款的
`reason`。`reveal_engine.dart:529` 已经在读 `data.flagsCollection.isObscured` 构造目标，所以这个
事实在引擎内是拿得到的。

## 附录：同一片区域的三条小观察（顺带记录，不必单独处理）

1. **`uiRevealNoScrollableContainer` 也盖住了「identifier 拼错」。** 文档里说 reveal 的核心场景
   就是"目标根本不存在"，所以合并大概是有意的；但拼错 identifier 时调用方拿不到任何提示。若发现
   2 采纳区分，这条可以顺带解决。

2. **`reachability: "pointer"` 与接入方 gesture policy 是两件事。** 前者说的是 Flutter 命中测试，
   后者决定 `ui.gesture.*` 会不会被放行。接入方若按收敛写法只放行少数 identifier，则绝大多数
   `pointer` 目标仍会 `uiGestureDenied`。照「按 reachability 分流 tap」字面实现会踩空，正确姿势
   是「`pointer` **且**在 gesture 允许集内才走 gesture，否则走 `ui.semantics.actionByIdentifier`」。
   值得在 reveal 的文档里点一句。（`uiGestureDenied` 会原样透传接入方 policy 的
   `rejectionNotice`，这点很好用。）

3. **`ui.reveal` 需要接入方注入 `revealPolicy` 才进 catalog，而候选分支上没有任何 0.5.0
   changelog 条目。** `revealPolicy` 是 `PatchbayFlutterBridge` 的可选具名参数，不注入时
   `bridge.reveal.enabled == false`、命令不进 catalog、直调 bridge 得 `uiRevealDisabled`
   （`test/reveal/reveal_policy_test.dart` 已锁）。这与 0.4.0 的 inspector / gesture 是同一种
   opt-in 形状，本身合理；问题是存量接入方**无从得知又多了第三块**——
   `packages/patchbay_flutter/CHANGELOG.md` 最新条目仍停在 0.4.1。定版时建议在 changelog 与升级
   说明里写明「`ui.reveal` 需注入 `revealPolicy`，否则命令不出现在 catalog 中」，否则每个升级
   上来的接入方都会先花一轮排查"命令面多了 3 条但 App 上只多了 2 条"。

## 已核对过、不是问题的两点

- **不是构建串味**：跑的确实是候选构建。判别式是 live catalog 里存在
  `ui.semantics.actionByIdentifier`，该命令在 `patchbay-v0.4.1` tag 的
  `lib/src/ui_protocol_commands.dart` 中零出现、在候选中存在。（`identity` 的 `serverVersion`
  仍报 `0.4.1`，因为候选分支尚未切版号，不能用它判别。）
- **不是遮挡判定粘滞**：关掉浮层后，同一目标的 `ui reveal` 立刻恢复 `outcome: revealed` /
  `reachability: pointer`，`ui tap` 恢复 `dispatched`。遮挡拒绝是状态驱动的，正确。
