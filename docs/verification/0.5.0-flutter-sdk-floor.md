# PB-050-12 最低 Flutter / Dart SDK 组合调查

> 状态：实现中——真实最早可安装组合已定位，但尚未全绿，需要 Linux CI 复核
>
> 关联：PB-050-12
>
> 调查日：2026-08-27

## 结论

`packages/{patchbay,patchbay_cli,patchbay_transport}/pubspec.yaml` 声明 `sdk: '>=3.11.0
<4.0.0'`；`packages/patchbay_flutter` 与 `example` 额外声明 `flutter: '>=3.38.0'`。这两条约束**不能
在同一个真实 Flutter release 上同时成立**：Flutter 官方 release 清单
（`releases_linux.json` / `releases_macos.json`）显示 3.38.0 至 3.38.10 全系只内置 Dart 3.10.0 至
3.10.9，任何声称「Flutter 3.38.0」的安装其自带 Dart 都无法满足 `>=3.11.0`。两个约束共同要求的**最早
可安装** release 是 **Flutter 3.41.0（内置 Dart 3.11.0，2026-02-11 发布）**——这是官方渠道里第一个
同时满足两条声明约束的版本。

以此为「最早可安装组合」候选，在本地 macOS arm64（沙盒环境唯一可用平台）用该组合完整跑
`pub get` / `analyze --fatal-infos` / `test`：五个 package 中四个（`patchbay`、`patchbay_cli`、
`patchbay_transport`、`example`）全部 resolve + analyze + test 通过；`patchbay_flutter` 本身
289 个测试里有 1 个失败——`test/reveal/reveal_matrix_test.dart` 的
「ModalBarrier 盖住已挂载目标 ⇒ targetBlocked，且不再继续滚动」。追到 3.41.x 全系最新补丁
（3.41.9）仍复现同一失败，说明这不是某个已被 cherry-pick 修掉的偶发缺陷。

继续往后找：官方 stable 渠道在 3.41.9 之后直接跳到 3.44.0（3.42/3.43 未在 stable 发布过）。3.44.0
和 3.44.1 上，前述 reveal 测试转绿，但换成另外三个测试失败（`target_catalog_bridge_test.dart` /
`semantics_tree_bridge_test.dart` / `text_target_bridge_test.dart`），报
`Exception: Asset 'shaders/ink_sparkle.frag' manifest could not be decoded: ... Unsupported
runtime stages format version. Expected 2, got 1`——一个与 patchbay 源码无关的引擎/着色器资产版本
不匹配。当前 CI 上界 Flutter 3.44.9 是本次调查里唯一确认五个 package 全部 resolve、analyze
（`--fatal-infos`）、test 全绿的组合（1497 个测试：490 + 669 + 29 + 289 + 20）。

**因此：不把「最早可安装」与「全绿已验证」混为一谈。** 最早可安装组合（Flutter 3.41.0 / Dart
3.11.0）是机检确定的事实，已接入 CI 作为非阻断 `sdk_floor` lane（`.gitlab-ci.yml` /
`.github/workflows/ci.yml`）。它现阶段还不是「已验证下限」——`allow_failure: true`，且下面两个
问题都还没有在真实 CI 用的 Linux 平台上复核过，只在本机 macOS arm64 复现过。

## 已知问题一：reveal 终止条件矩阵在 3.41.0–3.41.9 失败

`packages/patchbay_flutter/lib/src/reveal/reveal_engine.dart` 的 `_afterStep` 在每次派发滚动
action、等待 `_frames.nextFrameBefore(deadline)` 恰好一帧之后，读取
`mounted.areUserActionsBlocked` 判定目标是否被模态屏蔽。调试插桩确认：在 Flutter 3.41.0 上，
`test/reveal/reveal_matrix_test.dart` 里那一行**刚被 `ListView.builder` 滚动进视野**、由
`Semantics(blockUserActions: true, child: Semantics(identifier: ..., button: true,
onTap: ...))` 两层未声明 `container: true` 的 Semantics 合并而成的节点，`areUserActionsBlocked`
在这一帧读到的仍是 `false`。

缩小范围排除了这是遮挡判定普遍失效：

- `test/bridge/semantics_occlusion_admission_test.dart` 的
  「a blocked target keeps reporting uiSemanticsActionBlocked」用**完全相同**的两层 Semantics
  嵌套结构，只是从第一帧就静态构建（不在 `ListView` 里滚动挂载），在 3.41.0 上正常通过。
- `packages/patchbay_flutter/lib/src/occlusion/occlusion_probe.dart`（PB-050-16 的几何遮挡探针，
  point-like action 派发用的那一条通路）不受影响：`example` 的
  `example_occlusion_admission_test.dart` 在 3.41.0 上 20/20 全绿。

两条线索指向同一个更窄的结论：只在**一个刚被懒加载/滚动挂载的列表项**上，`blockUserActions`
配置合并进 `SemanticsNode.areUserActionsBlocked` 所需的时间，在 Flutter 3.41.x 的调度/语义 flush
管线上比 3.44.9 多至少一帧。本次调查未定位到框架侧具体修复提交（在本机可访问的
`packages/flutter` 完整历史里检索了 3.41.0..3.44.9 间 `semantics.dart` / `widgets/basic.dart` 的
改动，未见明显匹配的单个提交），也未验证这是否是 macOS arm64 特有的调度时序，还是 Linux 上同样
可复现的框架行为。这正是 `sdk_floor` lane 现在只非阻断跑的原因：需要它在真实 CI runner
（Linux x64）上的结果，才能判断这是要在 backlog 里另立一条缺陷跟踪，还是 macOS 本地噪音。

## 已知问题二：3.44.0 / 3.44.1 的着色器资产缺陷

`Unsupported runtime stages format version. Expected 2, got 1` 是 Flutter 引擎与其自带
`ink_sparkle` 着色器资产版本戳不匹配，与 patchbay 源码无关；触发它的三个测试都会走 Material
水波纹/墨溅效果。检索本机 `packages/flutter` 完整历史在 3.44.0..3.44.9 之间未见相关提交，说明这
更像是特定 release 的引擎构建产物缺陷，而不是框架源码变化——这类缺陷历史上往往具有平台/架构
相关性（Impeller 着色器编译在不同 OS/CPU 架构的构建管线上产出不同）。**本次调查全程只在 macOS
arm64 上复现，未排除这是否是该架构特有的构建缺陷、在 Linux x64 CI 上根本不出现。** 未继续
bisect 3.44.2–3.44.8 定位修复点（每个候选版本的官方 release archive 约 2 GiB，继续二分的时间
成本已超出本次调查预算）。

`patchbay`、`patchbay_cli`、`patchbay_transport` 三个纯 Dart 包在 3.41.0 上 `dart analyze
--fatal-infos` 均为 `No issues found!`——不同于旧一版调查（floor 定在 3.35.7 / Dart 3.9.2 时）记录
的「CLI 39 条版本特有 info」，Dart 3.11.0 不再触发那批 legacy-seam deprecation info，`--fatal-infos`
在这一层不需要放宽。

`packages/patchbay_flutter/lib/src/semantics/` 的 `PatchbaySemanticsAction.flutterAction`
exhaustive switch（`tap`/`longPress`/`focus`/`dismiss`/`showOnScreen`/`scrollUp`/`scrollDown`/
`scrollLeft`/`scrollRight`/`increase`/`decrease`/`expand`/`collapse`/`setText`）在 Flutter 3.41.0
上原样编译通过，不需要任何运行时兼容层。核实：`SemanticsAction.expand` / `.collapse` 由 engine
提交 `c6ffbdf7ea8`（2025-09-27，"[a11y] Add `expanded` flag support to Android."）首次引入，早于
3.38.0（2025-11-12 发布）与 3.41.0，因此这两个较新的 action 名字在 3.41.0 及以上版本里始终存在；
只有更早的 3.35.7 才会缺失它们。这意味着一份更早期、以 3.35.7 为候选下限的调查草案里提出的
「运行时按 `SemanticsAction.values` 名字解析、缺失时降级」兼容层，在真实最低下限 3.41.0
上是不需要的——没有随本次调查落地。

## 复现方法

```sh
# 取一份 SHA-256 固定的 release archive（示例用 3.41.0 的 Linux 版）
curl --fail --location --retry 3 \
  --output /tmp/flutter-3.41.0.tar.xz \
  https://storage.flutter-io.cn/flutter_infra_release/releases/stable/linux/flutter_linux_3.41.0-stable.tar.xz
echo "368ae5b6993c51861324e704c42d61c4e290fba7213a88fd0e9fec15ded54599  /tmp/flutter-3.41.0.tar.xz" | sha256sum -c -
mkdir -p /tmp/flutter-floor && tar --no-same-owner -xJf /tmp/flutter-3.41.0.tar.xz -C /tmp/flutter-floor
export PATH="/tmp/flutter-floor/flutter/bin:$PATH"

# 从仓库根目录运行
./tool/verify_sdk_floor.sh
```

`tool/verify_sdk_floor.sh` 只做 `pub get` / `analyze` / `test`，不构建原生平台产物；与现有
`flutter_package` CI lane 的验证范围对齐。
