> `sdk_floor` lane 钉 3.44.0 并转为阻断门禁。契约见
> [SDK 下限提升 Proposal](../proposals/0.5.0/sdk-floor-raise.md)

## 结论

`packages/{patchbay,patchbay_cli,patchbay_transport}/pubspec.yaml` 声明 `sdk: '>=3.11.0
<4.0.0'`；`packages/patchbay_flutter` 与 `example` 额外声明 `flutter: '>=3.38.0'`。这两条约束**不能
在同一个真实 Flutter release 上同时成立**：Flutter 官方 release 清单
（`releases_linux.json` / `releases_macos.json`）显示 3.38.0 至 3.38.10 全系只内置 Dart 3.10.0 至
3.10.9，任何声称「Flutter 3.38.0」的安装其自带 Dart 都无法满足 `>=3.11.0`。两个约束共同要求的**最早
可安装** release 是 **Flutter 3.41.0（内置 Dart 3.11.0，2026-02-11 发布）**——这是官方渠道里第一个
同时满足两条声明约束的版本。

以此为「最早可安装组合」候选，在本地 macOS arm64（沙盒环境唯一可用平台）用该组合完整跑
`pub get` / `analyze --fatal-infos` / `test`：五个 package 中四个（`patchbay`、`patchbay_cli`、
`patchbay_transport`、`example`）全部 resolve + analyze + test 通过；`patchbay_flutter` 本身
289 个测试里有 1 个失败——`test/reveal/reveal_matrix_test.dart` 的
「ModalBarrier 盖住已挂载目标 ⇒ targetBlocked，且不再继续滚动」。追到 3.41.x 全系最新补丁
（3.41.9）仍复现同一失败，说明这不是某个已被 cherry-pick 修掉的偶发缺陷。

继续往后找：官方 stable 渠道在 3.41.9 之后直接跳到 3.44.0（3.42/3.43 未在 stable 发布过）。3.44.0
和 3.44.1 上前述 reveal 测试转绿；初次调查在这两个版本上另外记录了三条
`Exception: Asset 'shaders/ink_sparkle.frag' manifest could not be decoded: ... Unsupported
runtime stages format version. Expected 2, got 1` 失败，**该结论已于 2026-08-27 证伪**——那是同一棵
工作树里跨 SDK 切换留下的构建缓存污染，不是 release 缺陷（见「已知问题二」节）。

**因此：不把「最早可安装」与「全绿已验证」混为一谈。** 最早可安装组合（Flutter 3.41.0 / Dart
3.11.0）是机检确定的事实，已接入 CI 作为非阻断 `sdk_floor` lane（`.gitlab-ci.yml` /
`.github/workflows/ci.yml`）。它现阶段还不是「已验证下限」——`allow_failure: true`；「已知
问题一」已经在真实 GitLab CI 的 Linux x64 runner 上跑出了与本机 macOS arm64 完全一致的失败，
确认不是 macOS 本地噪音，已登记 [PB-050-28](../backlog.d/PB-050-28.md) 跟踪。

**2026-08-27 追加，两条结论都变了：**

1. **「已知问题一」的根因已定位，它改变了这条 lane 的性质。** 不是仓内 `reveal_engine.dart` 的
   时序缺口，而是 3.41.x 不含 Flutter 上游提交 `af35e77c83d` 所致——在那之前 `Semantics(identifier:)`
   不构成语义边界，patchbay 整条 identifier 锚定安全模型赖以成立的前提在 3.41.x 上不成立。
   **这意味着 3.41.0 不可能通过「修仓内代码」变成已验证下限**，`sdk_floor` lane 的去向是一个下限
   口径裁决，不是一个实现任务。
2. **「已知问题二」被证伪，最早全绿组合因此下移到 3.44.0。** 清空五个包的 `.dart_tool` / `build`
   之后，**Flutter 3.44.0 跑完整 `tool/verify_sdk_floor.sh` 退出码 0、五个包 1498 个测试全绿**
   （490 + 669 + 29 + 290 + 20）。3.44.0 同时也是含 `af35e77c83d` 的第一个 stable——也就是说
   「最早全绿」与「最早语义正确」在 3.44.0 上重合，把下限提到这里没有已知残留阻塞。

## 已知问题一：reveal 终止条件矩阵在 3.41.0–3.41.9 失败

`packages/patchbay_flutter/lib/src/reveal/reveal_engine.dart` 的 `_afterStep` 在每次派发滚动
action、等待 `_frames.nextFrameBefore(deadline)` 恰好一帧之后，读取
`mounted.areUserActionsBlocked` 判定目标是否被模态屏蔽。调试插桩确认：在 Flutter 3.41.0 上，
`test/reveal/reveal_matrix_test.dart` 里那一行**被 `ListView.builder` 滚动挂载**、由
`Semantics(blockUserActions: true, child: Semantics(identifier: ..., button: true,
onTap: ...))` 两层未声明 `container: true` 的 Semantics 合并而成的节点，`areUserActionsBlocked`
读到的是 `false`（**而不是 `true`**）。于是 reveal 不走 `targetBlocked`，转而按「已露出」终止，
把一个被模态屏蔽的目标报成 `revealed`。

缩小范围排除了这是遮挡判定普遍失效：

- `test/bridge/semantics_occlusion_admission_test.dart` 的
  「a blocked target keeps reporting uiSemanticsActionBlocked」用**完全相同**的两层 Semantics
  嵌套结构，只是从第一帧就静态构建（不在 `ListView` 里滚动挂载），在 3.41.0 上正常通过。
- `packages/patchbay_flutter/lib/src/occlusion/occlusion_probe.dart`（PB-050-16 的几何遮挡探针，
  point-like action 派发用的那一条通路）不受影响：`example` 的
  `example_occlusion_admission_test.dart` 在 3.41.0 上 20/20 全绿。

> **以下这段初次调查时的推断已被 2026-08-27 的根因定位证伪，保留仅为记录：**
> ~~两条线索指向同一个更窄的结论：只在一个刚被懒加载/滚动挂载的列表项上，`blockUserActions`
> 配置合并进 `SemanticsNode.areUserActionsBlocked` 所需的时间，在 Flutter 3.41.x 的调度/语义 flush
> 管线上比 3.44.9 多至少一帧。~~ 实测证明**多等帧不会让这个值变成 `true`**，见下一节。

**Linux CI 复核（2026-08-27）：** `sdk_floor` lane 接入 GitLab 后，真实跑在 Linux x64 runner
（`ci13-general`）上——[pipeline 6028](http://gitlab.hirobot.in:9090/cloud/mobile/patchbay/-/pipelines/6028)
的 [job 27769](http://gitlab.hirobot.in:9090/cloud/mobile/patchbay/-/jobs/27769)——复现了**完全相同**
的失败：`test/reveal/reveal_matrix_test.dart` 的「ModalBarrier 盖住已挂载目标」，`Expected: 'failed'
/ Actual: 'revealed'`，逐字符与本机 macOS arm64 的失败输出一致；同一 job 里
`patchbay`/`patchbay_cli`/`patchbay_transport` 三个纯 Dart 包分别 490/669/29 测试全绿，与 macOS
结果同样一致。**这确认了这不是 macOS arm64 特有的调度时序噪音，是 Flutter 3.41.x 上一个真实的
跨平台缺陷。**

## 「已知问题一」的根因：3.41.x 不含上游 `af35e77c83d`

> 定位日：2026-08-27。复现环境：本机 macOS arm64，`storage.flutter-io.cn` 取 SHA-256 固定的
> `flutter_macos_arm64_3.41.0-stable.zip`（`24aa98db…44f6`）解压后 PATH 前置，未安装、切换或写入
> 全局 Flutter；对照组为本机默认的 3.44.9。

### 两条框架事实

**事实一：`Semantics(identifier:)` 在 3.41.x 上不构成语义边界。** Flutter 上游提交
`af35e77c83d`（`[framework] Fix Text.semanticsIdentifier being absorbed by ancestor nodes`，
PR #181795，2026-02-27 合入）把 `RenderSemanticsAnnotations.describeSemanticsConfiguration` 的

```dart
config.isSemanticBoundary = container;                              // 3.41.x
config.isSemanticBoundary = container || (_properties.identifier != null);  // 3.44.x
```

首个含该提交的 **stable** release 是 **3.44.0**；stable 渠道在 3.41.9 与 3.44.0 之间没有发布过任何
版本（3.42 / 3.43 只有 beta），因此 3.41.x 全系都不含它，也不会再有含它的 3.41.x 补丁。

**事实二：`SemanticsConfiguration.absorb` 从不把 `isBlockingUserActions` 复制给吸收方。** 这段代码
在 3.41.0 与 3.44.9 上逐字节相同：它在吸收一个 `isBlockingUserActions` 的子 config 时**只过滤该子
config 的 action handler**（只留 `_kUnblockedUserActions`，即两个 a11y focus 动作），不设置吸收方
自己的 `isBlockingUserActions`。而 `SemanticsNode._areUserActionsBlocked` 只有一个来源：
`config.isBlockingUserActions`。于是「吸收了一个被屏蔽子树」的节点，其 `areUserActionsBlocked`
恒为 `false`，同时它的有效 action 已经被掩掉。

### 两条事实相乘的后果

在 3.41.x 上，`Semantics(blockUserActions: true) > Semantics(identifier: …)` 这种写法里，两层
config 都不是边界，于是一起被并进**更上面**那个边界节点——在 `ListView.builder` 的行上，那是
`IndexedSemantics` 建的节点。该节点因此 `areUserActionsBlocked == false`。
在 3.44.x 上 identifier 自己成节点，`blocksUserActions` 经 `_SemanticsParentData` 正常下传，读到
`true`。

**这不是「多等一帧」。** 判别探针在同一节点上多等 3 帧，`areUserActionsBlocked` 仍是 `false`，
整条祖先链也全是 `false`，且该节点没有子节点——**这条信息根本不在语义树里**，等多少帧都不会
出现。

判别实验（同一探针、同一 fixture，两版本对照，读的是滚动挂载后目标节点的 `areUserActionsBlocked`）：

| fixture | 3.41.0 | 3.44.9 |
|---|---|---|
| `ListView` 行：`Semantics(blockUserActions:) > Semantics(identifier:)` | **`false`**（+3 帧仍 `false`） | `true` |
| 同上，但 identifier 一侧加 `container: true` | `true` | `true` |
| 同一 widget 静态构建（不进 `ListView`） | `true` | `true` |

第三行解释了为什么 `semantics_occlusion_admission_test.dart` 的静态用例在 3.41.0 上照常通过：它的
外层 `Semantics(blockUserActions: true)` 自己形成了节点（祖先下传的 `explicitChildNodes` 使然），
`isBlockingUserActions` 落在它**自己**的 config 上，根本不经过 `absorb`。所以「静态过、懒加载不过」
的差别不是构建时机，是节点边界落在哪里。

### 影响面（端到端实测，不是推断）

用真实 bridge 在两个版本上各跑一遍同一组 fixture：

| 入口 | 3.41.0 | 3.44.9 |
|---|---|---|
| `ui.semantics.tap`，静态被屏蔽目标（仓内既有用例形状） | `uiSemanticsActionBlocked`，回调 0 次 | 同左 |
| `ui.semantics.tap`，**同一 widget 挂在懒加载列表行上** | **`uiSemanticsActionUnavailable`**，回调 0 次 | `uiSemanticsActionBlocked`，回调 0 次 |
| 同上，identifier 一侧加 `container: true` | `uiSemanticsActionBlocked`，回调 0 次 | 同左 |
| `ui.reveal`，懒加载列表行上的被屏蔽目标 | **`revealed` + `reachability: pointer`** | `failed` / `targetBlocked` |

两条结论必须分开说，不要混为一谈：

1. **防误击闸本身没有被击穿。** 上表三种 `ui.semantics.tap` 情形回调都是 **0 次**——框架把被屏蔽
   节点的 action 位掩掉了，`_dispatch` 的 `hasAction` 复核接住了它。3.41.x 上不存在「点穿一个被
   模态屏蔽的目标」。
2. **但对外语义在 3.41.x 上是错的，且 `ui.reveal` 那一格是真正的 fail-open。**
   - `ui.semantics.*` 用 `uiSemanticsActionUnavailable` 顶替了 `uiSemanticsActionBlocked`。
     [PB-050-16 正文](../proposals/0.5.0/semantics-occlusion-admission.md)明确要求这两件事不串码
     （「补救方式不同……合并成一个码会让接入方无法定位」），串码本身就是它要避免的诊断塌陷。
   - `ui.reveal` 按契约**不查 action**（`semanticsOnly` 目标本来就允许没有 action），因此没有第二道
     兜底，直接把一个被模态屏蔽的目标报成 `revealed` + `reachability: pointer`。这违反
     [PB-050-17 的终止条件矩阵](../proposals/0.5.0/semantics-scroll-reveal.md)冻结的
     「目标挂载且 `areUserActionsBlocked` ⇒ `failed` / `targetBlocked`」。

### 为什么没有在 `reveal_engine.dart` 里修

三条路都试过，都不成立：

1. **「多等一帧再读」不成立**——根因不是时序，多等 3 帧值不变（上表第一行），所以它连症状都治
   不了。退一步说即使有效也不能用：它会给 3.44.9 的每步 cadence 多加一帧，违反
   [PB-050-17](../proposals/0.5.0/semantics-scroll-reveal.md) 冻结的步序（第 i 步「恰好一帧」），
   并可观测地改变同一次调用的 `afterTreeRevision` 与 deadline 消耗——而 PB-050-07 的裁决二正要求
   实际驱动的帧必须如实计入、不得隐瞒，这条改动无法悄悄做。
2. **「版本感知兼容层」无物可补**——需要的信息不在语义树里，不是晚到。探测到版本之后也没有
   任何可读的替代信号：目标节点自身、整条祖先链的 `areUserActionsBlocked` 全是 `false`，节点无
   子节点，`SemanticsData` 也没有区分「action 被掩掉」与「本来就没有该 action」的字段。
3. **唯一能恢复该信息的通路是走渲染树**（解析目标的 `RenderObject` 锚点，逐个重新求值
   `describeSemanticsConfiguration` 找 `isBlockingUserActions`）。这是在安全边界内新造机制：它重复
   实现框架内部逻辑、依赖 `debugSemantics`（`kReleaseMode` 下为 null，于是 release 与 debug 的
   `targetBlocked` 判定会分叉），并直接改动 PB-050-16 冻结的「不修改 `areUserActionsBlocked` 的
   既有含义」。按 `AGENTS.md` 与该 Proposal 的接缝纪律，这不是实现 MR 能静默做的事。

### 待裁决：下限口径

事实层面已经确定：**patchbay 的 identifier 锚定安全模型要求 `Semantics(identifier:)` 自成语义节点，
而上游只从 `af35e77c83d`（stable 首见于 3.44.0）起提供这一保证。** 因此 3.41.x「可安装」但不满足
PB-050-10 / PB-050-16 / PB-050-17 共同依赖的语义前提。两条可选口径，由仓主裁决：

- **口径 A：把声明的 Flutter 下限提到含该提交的第一个 stable，即 3.44.0**，`sdk_floor` lane 改跑
  3.44.0 并**去掉 `allow_failure`**。代价一度被认为是「3.44.0 / 3.44.1 还压着已知问题二」——
  **该顾虑已消除**：已知问题二被证伪为本地缓存污染，3.44.0 清缓存后跑完整
  `tool/verify_sdk_floor.sh` 退出码 0、五包 1498 个测试全绿。
- **口径 B：维持现有声明**，把 3.41.x 记为「可安装但语义不受支持」，`sdk_floor` lane 长期保持
  `allow_failure` 并在 lane 注释里写明它测的是「可安装性」而不是「语义正确性」。

### 裁决结论（2026-08-27，仓主在会话中裁决）

**采用口径 A。** 完整论证、契约与被否决方案见
[SDK 下限提升 Proposal](../proposals/0.5.0/sdk-floor-raise.md)（状态：已接受）。落地内容：

- 四个 package 与 `example` 的声明下限改为 **Flutter `>=3.44.0` / Dart `>=3.12.0`**——这是这两个
  数字第一次指向同一个真实 release，也是第一次指向一个被机检证明全绿的组合。
- `sdk_floor` lane（GitLab 与 GitHub 两边）钉 3.44.0 并**摘掉 `allow_failure` / `continue-on-error`**，
  语义从「探测性非阻断」转为「已验证下限的守门」：跑红即代表声明下限不再成立，必须阻断。两件事在
  同一提交内完成——先摘 `allow_failure` 会把主线打红（lane 还跑着必然红的 3.41.0），先换版本不摘则
  这条 lane 仍然不设防。
- 下限选 3.44.0 而不是更保守的 3.44.9：3.44.0 已被完整 `verify_sdk_floor.sh` 证明全绿，再加保守
  余量只会无理由排除 3.44.0–3.44.8 的接入方。
- **不为 3.41.x 写兼容层**，PB-050-28 按「上游缺陷、经下限提升消解」收尾，本仓不改一行实现代码。

至此「最早可安装」「最早语义正确」「最早全绿」「声明下限」四个口径在 Flutter 3.44.0 上合一，
本文开头「不把最早可安装与全绿已验证混为一谈」的分裂状态结束。

## 已知问题二：**已证伪**——不是 release 缺陷，是跨 SDK 构建缓存污染

> 结论更新：2026-08-27（PB-050-28 根因排查顺带查清）。**3.44.0 在清空构建缓存后五个包全绿。**

初次调查的记录是：3.44.0 / 3.44.1 上三个走 Material 水波纹的测试报
`Exception: Asset 'shaders/ink_sparkle.frag' manifest could not be decoded: INVALID_ARGUMENT:
Unsupported runtime stages format version. Expected 2, got 1`，据此推测为「特定 release 的引擎
构建产物缺陷，可能与 macOS arm64 架构相关」。

**这个推测是错的。** 两条实测证据：

1. **在已知全绿的 3.44.9 上复现出了完全相同的异常。** 本次排查先用 3.41.0 在
   `packages/patchbay_flutter` 里跑过测试，随后不清缓存直接切回 3.44.9 跑，得到 `+287 -3`，三条
   失败全部是同一条 `ink_sparkle.frag` / `Expected 2, got 1`。删掉 `.dart_tool` 与 `build`
   重跑，同一个 3.44.9 立刻回到 `+290` 全绿。**同一个 SDK、同一份源码，差别只有缓存。**
2. **3.44.0 清缓存后自己就是全绿的。** 清掉五个包的 `.dart_tool` / `build` 后用 3.44.0 跑完整的
   `tool/verify_sdk_floor.sh`：**退出码 0，五个包全部 resolve + analyze + test 通过，共 1498 个
   测试（490 + 669 + 29 + 290 + 20）**，日志里一次 `ink_sparkle` 都没有出现。

成因是资产 manifest 的 runtime-stages 版本戳由**生成它的那个 SDK** 决定，而缓存留在包目录里不随
SDK 切换失效；下一个 engine 版本读到旧戳就报 `Expected 2, got 1`。初次调查在同一棵工作树里依次跑
3.41.0 → 3.44.0 → 3.44.1 而没有在版本之间清缓存，于是把自己制造的污染记成了 release 缺陷。

**操作纪律（写进流程，避免再犯）：在同一棵工作树里切换 Flutter 版本跑测试，必须先删掉每个包的
`.dart_tool` 与 `build`。** `tool/verify_sdk_floor.sh` 自己不清缓存——CI lane 每次都是干净
容器所以不受影响，但本地复现必须手工清。

未复跑 3.44.1（与 3.44.0 同代同 engine 线，没有理由预期不同）；原先「若有余力二分 3.44.2–3.44.8」
这一项随本条一并作废——不存在需要被二分的缺陷。

`packages/patchbay_flutter/lib/src/semantics/` 的 `PatchbaySemanticsAction.flutterAction`
exhaustive switch（`tap`/`longPress`/`focus`/`dismiss`/`showOnScreen`/`scrollUp`/`scrollDown`/

只有更早的 3.35.7 才会缺失它们。这意味着一份更早期、以 3.35.7 为候选下限的调查草案里提出的
「运行时按 `SemanticsAction.values` 名字解析、缺失时降级」兼容层，在真实最低下限 3.41.0
上是不需要的——没有随本次调查落地。

## 复现方法

```sh
# 取一份 SHA-256 固定的 release archive（示例用 3.41.0 的 Linux 版）
curl --fail --location --retry 3 \
  --output /tmp/flutter-3.41.0.tar.xz \
  https://storage.flutter-io.cn/flutter_infra_release/releases/stable/linux/flutter_linux_3.41.0-stable.tar.xz
echo "368ae5b6993c51861324e704c42d61c4e290fba7213a88fd0e9fec15ded54599  /tmp/flutter-3.41.0.tar.xz" | sha256sum -c -
mkdir -p /tmp/flutter-floor && tar --no-same-owner -xJf /tmp/flutter-3.41.0.tar.xz -C /tmp/flutter-floor
export PATH="/tmp/flutter-floor/flutter/bin:$PATH"

# 关键一步：在同一棵工作树里切换 Flutter 版本之前必须清掉每个包的构建缓存。
# 资产 manifest 的 runtime-stages 版本戳由生成它的那个 SDK 决定，缓存不随 SDK 切换
# 失效；漏了这步会得到 `ink_sparkle.frag ... Expected 2, got 1` 这类假失败——
# 「已知问题二」当初就是这么被误记成 release 缺陷的。CI 每次是干净容器，不受影响。
for d in packages/patchbay packages/patchbay_cli packages/patchbay_transport \
         packages/patchbay_flutter packages/patchbay_flutter/example; do
  rm -rf "$d/.dart_tool" "$d/build"
done

# 从仓库根目录运行
./tool/verify_sdk_floor.sh
```

`tool/verify_sdk_floor.sh` 只做 `pub get` / `analyze` / `test`，不构建原生平台产物；与现有
`flutter_package` CI lane 的验证范围对齐。
