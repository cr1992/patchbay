# PB-050-04 Semantics probe 帧放大量测

> 状态：已验证
>
> 日期：2026-08-25

## 结论

当前热点首先是帧调度，不是小树上的 identifier 扫描。Android 16 真机 profile 会话中，固定版本的
example 树有 35 个 Semantics 节点；一次 identifier probe 的中位耗时为 8.598 ms，其中
`ensureOwner` 为 8.465 ms，扣除后的扫描独占估算只有 0.133 ms。未命中的 semantics `ui.wait` 每轮先由
probe 主动等待一帧，再由 wait cadence 等一帧，稳定产生 2 帧放大。

PB-050-07 应优先裁决如何消除这两次连续等待，同时保持 owner/tree 失效、`elapsedMs`、
`frameRevision`、timeout 与 generation 复核语义。identifier index 暂不应作为第一步；只有更大树规模的
profile 数据证明扫描成为主成本后才实现。

## 复现方法

固定结构 harness 位于
`packages/patchbay_flutter/test/semantics_probe_benchmark_test.dart`，运行：

```sh
cd packages/patchbay_flutter
flutter test test/semantics_probe_benchmark_test.dart --reporter expanded
```

测试输出以 `PB05004_METRICS=` 开头的单行 JSON，方便 CI 提取。它构造 256 个明确 Semantics target，
实际树为 260 个节点，预热 2 次后采样 12 次。JIT widget-test 的微秒数只用于验证 harness 和分段关系，
不作为设备性能结论；稳定断言只覆盖扫描节点数和每段实际观察到的帧数。

正式时延从 Android 真机 profile example 会话获取：

```sh
export PATCHBAY_EXAMPLE_MODE=profile
source tool/example_session.sh
example_session_start <device-id>
example_session_cli --transport-timeout-ms 60000 --json exec \
  example.benchmark.semanticsProbe --args '{"samples":20}'
example_session_stop
```

命令是 example 自有的中性 benchmark 面，只在非 release host 中存在；它不进入四包公共命令 namespace，
不改变 Semantics、`ui.wait` 或协议行为。

## 结果

### 固定 256 target 的结构 harness

| 阶段 | 扫描节点 | 每次观察帧数 | 用途 |
|---|---:|---:|---|
| raw `endOfFrame` | — | 1 | 单帧等待基线 |
| `ensureOwner` | — | 1 | 证明 owner 已存在时仍主动请帧并等待 |
| missing identifier probe | 260 | 1 | 证明扫描前包含一次 owner 帧 |
| `ui.wait` additional frame | — | 1 | 证明未满足后 cadence 再等一帧 |

由后两行直接得到：一次未满足的 semantics wait poll 为 2 帧。该事实由计数断言冻结，不依赖机器速度。

### Android 真机 profile，20 次采样

| 阶段 | median | min | max | median frames |
|---|---:|---:|---:|---:|
| raw `endOfFrame` | 8.392 ms | 6.687 ms | 9.791 ms | 1 |
| `ensureOwner` | 8.465 ms | 7.222 ms | 13.822 ms | 1 |
| missing identifier probe（35 nodes） | 8.598 ms | 7.294 ms | 9.803 ms | 1 |
| `ui.wait` additional frame | 8.081 ms | 6.770 ms | 9.842 ms | 1 |

派生值：扫描独占中位估算 `8.598 - 8.465 = 0.133 ms`；一次未满足的 semantics wait poll 中位需要
`1 + 1 = 2` 帧。估算只用于判断优化顺序，不将两个相关样本相减后的值当作稳定 SLA。

## PB-050-07 决策输入

1. 先裁决 owner 已存在且 root 可用时是否允许跳过主动请帧，以及 owner/tree 变化如何失效；这是最大且每次
   必付的成本。
2. 将 semantics probe 自己等待的帧与 `ui.wait` cadence 放进同一时序模型，目标是未满足的一轮最多等一帧；
   必须同时冻结 `elapsedMs`、`frameRevision` 和 timeout 的兼容变化。
3. identifier index 继续作为条件方案。后续至少补 1k/10k 节点 profile 曲线，证明扫描成本超过帧等待后
   才值得引入缓存失效与 node identity 风险。
4. 无论采用何种优化，都继续执行 owner/tree identity、node identity、generation 和门后二次复核；本量测
   不授权改变这些安全围栏。

## 本 MR 的行为边界

本条只新增可复现 benchmark、example profile 入口和决策报告，不修改 production Semantics bridge、
请帧策略、wait cadence、缓存、generation 或稳定响应字段。普通功能真机矩阵按版本批次聚合执行；本条因
需要性能数字，额外单独完成了 Android 真机 profile 采样。
