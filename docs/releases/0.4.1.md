# Patchbay 0.4.1 版本计划

> 状态：规划中
>
> 范围真源：本文定义 0.4.1 的优先级、依赖和退出条件；[backlog](../backlog.md)
> 保存条目标题、动机、目标版本与实施状态。
>
> 发布方式：从稳定 `main` 创建 `release/0.4.1`；实现 MR 以该分支为目标，通过
> RC 门禁后再由一个发布 MR 合回 `main`。

## 版本定位

0.4.1 是 0.4 系列的内部质量版本，不扩展公共 API、wire、命令 descriptor、稳定 JSON、
状态机或安全边界。本版只做四件事：

1. 让四包的 pub.dev 评分在真实发布 archive 上可复现、可阻断、可回查；
2. 拆解 CLI、core 与 Flutter host 的高冲突文件，按领域建立可读的目录和依赖方向；
3. 用源码预算、测试结构和兼容 golden 阻止新职责重新堆回大文件；
4. 建立发布 finalize 机制，使已发布范围、延期范围和未结验收证据不再混在一张表里。

当前基线中，排除生成物后有 10 个生产文件超过 800 行、5 个测试文件超过 1,000 行；
`runPatchbayCli`、`PatchbayServiceHost` 和 `PatchbayFlutterServiceHost` 的两层影响面分别达到
85、115 和 52 个符号。0.4.1 不以“多建几个文件”为完成，而以职责边界、依赖方向和行为零漂移为完成。

## 范围分级

### P0：发布阻断

| 编号 | 关键验收 |
|---|---|
| PB-041-01 | 对四个实际发布 archive 使用 pub.dev 当期 Pana 跑出零扣分；同版内部依赖用临时本地解析消除假扣分；发布后 score API 的 `grantedPoints == maxPoints` 并留存脱敏结果 |
| PB-041-02 | finalize 先生成“已发布 / 已延期 / 仅缺证据”计划，再由 maintainer 显式 apply；不能批量删除“实现中”或把未结真机验收冒充完成 |
| PB-041-03 | 建立源码结构规范（[docs/code-structure.md](../code-structure.md)）并落地对应门禁：判红只针对结构错误——手写 `part` 碎片、跨包 `src/` 私有导入、越出包根的相对导入、领域目录循环依赖；函数与文件体积一律为警戒线，拆分与否按规范逐处判断并在 MR 描述中记录理由 |
| PB-041-06 | 超过 1,000 行的手写测试全部按行为域拆分，新建/完成拆分的测试文件不超过 700 行；共用 fixture 不吞断言、不合并原本独立的边界用例，重构前后测试清单可对账 |

### P1：本版目标

| 编号 | 关键验收 |

| PB-040-38 | Manifest walkthrough、snapshot diff 与 job wait 从 `cli.dart` 提取为独立 Runner；已有命令帮助、JSON、stderr、退出码与超时语义的 golden 不变 |
| PB-041-07 | 将 CLI registry、manifest、trace、doctor、session 依次拆成模型、解析、存储、执行与呈现组件；每批只改一个热点，CodeGraph 影响面和行为 golden 在 MR 中前后对账 |
| PB-040-40 | 在 CLI 职责边界稳定后完成 `commands/`、`workflows/`、`platform/`、`session/`、`manifest/`、`trace/`、`support/` 分层；公共 export、bin 入口、descriptor 与兼容语料零漂移 |
| PB-041-04 | 将 core host 的 VM Service 接入、snapshot、invoke、审计与 schema 校验拆为可注入服务，并按领域归档其余 core 文件；公共 barrel export 与协议 surface 不变 |
| PB-041-05 | 将 Flutter host 的 descriptor/decoder/注册编排和 semantics/gesture 查询执行分离，并按领域归档 bridge；debug/profile、direct/VM Service 与生命周期拒绝语义不变 |

### P2：本版不排期

不用低优先级新功能填充补丁版；P0/P1 完成后直接进入 RC。

## 明确不进入 0.4.1

- PB-040-24 轨迹回放、PB-040-30 引导式会话恢复、PB-040-31 长流程进度面和
  PB-040-32 字段级敏感输入都会新增或改变公共契约，继续留在 backlog 并先过 Proposal。
- PB-040-28 继续受上游采集前脱敏能力阻塞，不以“先收集再脱敏”降级安全边界。
- PB-040-33 至 PB-040-37 涉及系统弹窗、真机权限事实源和 App 重启/重附加，按平台专项版本另行规划。
- `text.set` formatter 与 `text.enter` submit 回调属于公共行为变更，未经 Proposal 不改写
  0.4.0 已发布契约。

## 依赖与实施顺序

1. **M0：版本与基线**——开建 `release/0.4.1`，冻结公共 surface、命令输出、测试清单和超限文件清单；
2. **M1：安全网**——先做 PB-041-03 与 PB-041-06，再分别落 PB-041-01、PB-041-02；门禁先于大规模移动生效；
3. **M2：平台底座**——PB-040-39 独立合入，为 CLI 后续拆分提供可注入系统边界；
4. **M3：CLI 入口**——PB-040-38 提取 Runner，先冻结行为 golden 再移动实现；
5. **M4：CLI 领域**——PB-041-07 按 registry → manifest → trace → doctor/session 顺序拆分，随后由 PB-040-40 归档目录；修改同一热点的 MR 必须串行；
6. **M5：core**——PB-041-04 先拆 `service_host.dart`，再归档 core 领域；不和 Flutter host 改动并行；
7. **M6：Flutter**——PB-041-05 在 core 边界冻结后拆 host 与 UI bridge；
8. **RC**——冻结范围，只接发布阻断修复，跑完结构预算、兼容、双模式 example 与 pub 门禁。

同一阶段可以包含多个独立 MR，但单个 MR 只拆一个职责边界，并且必须可独立回退。禁止一次性全仓
搬目录、跨包同时改热点，或把实现复制到新文件后保留两套路径。

## 验证与退出条件

- 四包 format、analyze `--fatal-infos`、test、codegen/check 与 `release_prep --version 0.4.1 --check`
  全绿；
- 结构预算检查全绿：生成物除外，无手写生产文件超过 800 行、无手写测试超过 1,000 行；新建或完成
  拆分的生产/测试文件分别不超过 600/700 行，且超限 ratchet 从 M0 起只降不升；
- 包间只能通过公开入口依赖，领域目录依赖方向无环；不得以 `part`、空转发文件或重复实现规避预算；
- 0.4.0 host ↔ 0.4.1 CLI、0.4.1 host ↔ 0.4.0 CLI 的兼容语料全绿，公共 catalog、
  response schema、错误码与退出码无未裁决变化；
- 每个重构 MR 先增加或冻结 characterization/golden，再移动实现；MR 描述记录拆分前后的文件行数、
  CodeGraph 影响面、测试清单和可独立回退点；
- `tool/example_precheck.sh` 的 debug 主链全绿，`tool/example_profile_smoke.sh` 的 profile
  答复形态全绿；两者都复用同一份指纹 AOT CLI；
- 四个实际发布 archive 在 pub.dev 当期 Pana 下无扣分，发布后 score API 确认
  `grantedPoints == maxPoints`；
- README、guide、包 README、架构 SVG 与发布阶段一致：开发期不提前宣称 0.4.1 已发布，
  发布候选只描述已经验收的 0.4.1 能力；打 tag 前通过 `documentation-current`；
- 发布 MR 合回 `main` 后，同一 SHA 同步 GitHub、打 `patchbay-v0.4.1` 并按依赖顺序
  发布四包；随后运行 finalize、将本文标为已发布并回收 `release/0.4.1`。

## 回退边界

本版不引入数据迁移或新协议。任一实现 MR 都必须能独立回退；若重构后出现行为漂移，
直接回退该 MR，不在 RC 中为保留新目录结构而改写旧契约。若某个拆分无法在一次 MR 内同时满足
行为 golden 与结构预算，先缩小拆分边界，不以跨 MR 暂存两套实现或临时兼容分支过渡。
