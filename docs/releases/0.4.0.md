## 版本目标

把 0.3.0 已有的“可观察、可调用”能力补成一条可靠的自动化闭环：

1. CLI 能稳定启动、选择并监督一个会话；
2. 操作者能按稳定 identifier 定位目标，执行长按、拖拽和 fling；
3. 操作继续服从声明门、生命周期门和 generation 围栏，不退化成任意坐标点击；
4. 操作前后能用 manifest、snapshot、capture 与 DevTools 证据验证结果；
5. 新命令从同一份 descriptor 生成注册、校验、帮助和文档，降低继续扩展的冲突成本。
6. 一次跨命令、跨重连的调试过程能被持久化、导出和比较；
7. AI 能预检和规范化原生权限，并通过平台 driver 处理预期系统弹窗后安全恢复调试链。

0.4.0 以“尽量清空当前 backlog”为目标。目标版本标为 0.4.0 的特性全部进入范围，但不是每项都能
无条件阻塞发布：安全边界未裁决、外部验证未完成或收益不足以覆盖风险的条目，必须通过范围变更 MR
明确退回 backlog，不能静默消失或带着未验证实现发布。PB-040-24 回放已显式留在 backlog 待排期，
先稳定 recorder 与平台权限 driver，不进入本版范围。

## MR 契约

每个实现 MR 必须：

1. 在中文描述中写明 `Plan: PB-040-XX`、用户结果、协议/安全影响和验收命令；
2. 一个 MR 承担一个可独立评审、验收和回退的交付单元；同一公共契约或热点调用链应合并，跨条目时解释不可拆原因；
3. 新行为带能验证“先红后绿”的测试，并覆盖 VM/direct 或明确说明为何只适用一条传输；
4. 公共 API、协议、默认上限或安全边界变化同步更新专题文档和 CHANGELOG 碎片；
5. design-gate 条目在裁决 MR 合入前不得进入实现 MR。
6. 满足 Proposal 门禁的条目必须引用已接受方案；实现偏离时先修改 Proposal 并重新评审。

本版功能 MR 目标为 `main`（版本分支模型自 0.5.0 起适用）。推荐分支名使用 `feature/040-<topic>`；自动化代理创建的分支继续使用其约定前缀。

## 范围变更规则

- **新增**：必须说明为何属于版本目标、依赖哪一项，以及替换或消耗哪部分验证预算。
- **延期**：必须提交范围变更 MR，记录未满足的证据、风险和回到 backlog 后的状态。
- **禁止静默降级**：不得为了按期发布而删除测试、放宽 fail-closed、隐藏 capability 或绕过设计闸门。
- **缺陷优先**：0.4 开发期间发现的回归先修复，再继续新增能力；涉及已发布版本时独立评估补丁版。

## 范围变更记录

本节记录已裁决的范围变更，供退出条件和 backlog 状态引用；一条记录写定后不再改写历史，后续调整另起编号。

### SC-040-01：发布判据从「两个接入方」改为「双平台 example 预检」

- **裁决**：2026-08-19，仓主。
- **变更**：本版的发布阻断判据是**本地 example 端到端预检在 Android 与 iOS 真机各跑全绿**。原先按
  「至少两个接入方」计数的条目（PB-040-01、PB-040-11、PB-040-12、PB-040-14、PB-040-21、PB-040-23）
  改为：预检通过即满足基本条件，接入方真机证据继续收集但属**补充**，不再是发布阻断项。
- **动机**：本版窗口内只有一个接入方在跑端到端验收，第二接入方不在本版范围。继续按接入方计数会让已经
  实现并有测试的能力永久停在「实现中」，把发布卡在一个本版拿不到的证据上。
- **放弃的证据**（预检证明不了、必须知道的四类）：真实领域控制器语义与设备 SDK 的完成确认；真实 UI 的
  嵌套滚动与遮挡；签名真机上的系统权限弹窗与首次授权路径；接入方跨版本 pin 的升级路径。`example` 是
  中性占位应用，这四类只有接入方能出证据。
- **风险与对冲**：预检全绿仍可能在真实 App 上暴露上述四类问题。对冲是接入方证据继续按补充收集，缺口在
  本节登记；补充证据发现的缺陷按「缺陷优先」处理，必要时走补丁版，不回改本版判据。
- **不放宽的部分**：预检仍是接入方验收的前置门；平台矩阵（Android 与 iOS 各一次真机会话、P0 权限集合、
  HarmonyOS 不宣称支持）、fail-closed 语义、测试与 codegen 门禁一律不变。删测试、放宽 fail-closed、
  隐藏 capability 仍属禁止的静默降级。

### SC-040-02：权限交付收窄为 Android 状态与规范化

- **裁决**：2026-08-19，仓主。
- **变更**：0.4.0 只把 Android adb 的 `capabilities/status/normalize/reset/fail` 纳入发布承诺，覆盖
  camera、microphone、locationWhenInUse、notifications 四个 P0 权限；写操作后必须复核设备事实，
  不可达状态必须先拒绝且不改变设备。系统弹窗 `exercise`、`allowOnce` decision 的端到端承诺、iOS
  `status/normalize/exercise`、Android/iOS reference runner、弹窗后的恢复闭环，以及五类 permission 专用
  trace 事件退出本版范围，PB-040-26 清除目标版本并回到 backlog。
- **保留的契约**：权限 wire、CLI 命令、`allowOnce` 状态词与 external driver protocol 不删除，避免把已形成
  的公共表面做成破坏性变更；但它们不等于 0.4.0 已支持的设备能力。CLI 只能按设备与已安装 runner 的
  实际探测发布 capability，缺少证据时稳定返回 unavailable/unsupported，不能因路径存在或 shell 退出 0
  假报成功。
- **动机**：仓内已在 Android 真机验证 adb 状态读取、`normalize granted`、`reset`、幂等、未声明权限和
  不可达 `denied` 的先拒绝不写设备；跨 OEM 系统弹窗没有通用稳定标识，官方 UiAutomator helper 也不能
  识别当前验证设备，iOS 则没有本版真机证据。继续把两套 runner 和弹窗矩阵作为 P0 会让发布绑定到尚未
  成立的平台假设。
- **风险与降级**：0.4.0 不能替用户自动完成首次授权弹窗，也不保证 iOS 权限状态规范化；调用方需人工处理
  弹窗、使用自有测试 driver，或把权限预置到目标状态。对外文档和 capability 必须明确这个边界；不得把
  fake-driver、源码 adapter 或单元测试写成真机支持。
- **不放宽的部分**：公共协议测试、driver 身份绑定、debug/test App 限制、写后复核、错误类型、
  fail-closed、Android 四项 P0 真机矩阵以及既有功能回归门禁不变。后续恢复 PB-040-26 时仍须先有可构建
  reference runner，并分别提交 Android OEM 基线和 iOS Simulator/真机证据。

### SC-040-03：Android 权限真机门禁按事实面与代表性写路径拆分

- **裁决**：2026-08-20，仓主授权按降级方案优先发布 0.4.0。
- **变更**：四个 P0 权限都必须在 Android 真机上通过 capability/status 的设备事实读取；写路径的
  `normalize granted`、幂等重放、不可达 `denied` 先拒绝不写设备与 `reset`，由 camera 作为代表性权限
  在仓内 example 上完成端到端预检。其余权限的 platform permission 映射和状态转换继续由 adapter
  单元测试覆盖，不再要求每项写操作都在同一台真机重复一遍。
- **动机**：Android 撤销已授予权限会终止被试 App，逐权限完整写矩阵需要在每一格之间重新建立会话，
  增加的是重复设备编排与 OEM 运行成本，而不是新的协议、身份绑定或写后复核语义。现有真机证据已覆盖
  四项可读事实，以及 camera 的完整写路径；接入方矩阵还补充覆盖了 microphone 与 location 的授权事实。
- **风险与降级**：不同 Android 版本仍可能对某个具体 platform permission 有独立限制。capability/status
  必须继续逐权限按设备事实 fail-closed；未读到声明或设备事实时不得外推可写。若后续恢复弹窗 exercise，
  仍须按 PB-040-26 单独建立逐权限、逐 decision 的设备矩阵，本裁决不替代该门禁。

### SC-040-04：iOS example 门禁降级为 Simulator，真机证据由接入方补足

- **裁决**：2026-08-20，仓主授权按降级方案优先发布 0.4.0。
- **变更**：最终候选 SHA 的双平台 example 门禁改为 Android 真机与 iOS Simulator 各一次全量预检；
  iOS 仍须有至少一个接入方在真机上跑通过 0.4.0 公共能力主链，但该接入方不必为最终候选重复签名。
  iOS 权限自动化已由 SC-040-02 退出本版，因此 Simulator 预检不得被表述为权限真机证据。
- **动机**：当前本机只有业务 App 的精确 provisioning profile 包含测试 iPhone；patchbay example 的
  通配 profile 不包含该设备，Xcode 又没有可用于自动更新 profile 的已登录账号。借用业务 bundle identity
  会覆盖已安装 App，也会把仓内中性 example 绑定到业务身份，不属于可接受的发布操作。另一方面，接入方
  已在同一台 iPhone 真机上跑通 0.4.0 的 identity/catalog/snapshot、诊断树、手势、导航、capture、logs、
  perf 与 keep-awake 主链，最终候选再由 Simulator 固定协议、CLI 与 host 接线即可覆盖本版剩余风险。
- **风险与降级**：最终 SHA 没有中性 example 的 iOS 真机安装证据，签名、安装与真实设备 lifecycle 的回归
  依赖接入方已有结果。对冲是保留 iOS Simulator 全量预检、接入方真机证据与现有 iOS 单元/集成测试；
  后续 Xcode 账号/profile 恢复后补跑 example 真机，但不阻断 0.4.0。系统弹窗真机证据按 SC-040-05 只由
  接入方 App 提供，example Simulator 不替代它。

### SC-040-05：恢复 iOS XCUITest 真机权限闭环，保留事实源降级

- **裁决**：2026-08-20，仓主授权在接入方 iPhone 真机打通后纳入 0.4.0。
- **变更**：恢复 PB-040-26 的 iOS 子集。仓内提供可构建的 XCUITest reference runner；显式配置签名
  `.xctestrun` 后，物理真机可对 camera、microphone、locationWhenInUse 执行 `reset/exercise`，覆盖
  allow/deny，locationWhenInUse 另覆盖 `allowOnce`。App 负责发起权限请求，runner 只验证并处理预期系统
  弹窗；处理后由既有恢复协议等待 App resumed、重连并刷新 catalog 与目标 generation。
- **证据**：真实接入方 iPhone 上已完成 microphone allow/deny、camera allow、locationWhenInUse
  allowOnce，三项均先 reset 到 `notDetermined`，弹窗结果为 `uiObserved`，且恢复到同一 App 实例；完整
  中性矩阵见[验证报告](../verification/ios-permission-xcuitest.md)。
- **风险与降级**：物理真机 `status/normalize` 仍没有权威公共事实源，保持 unsupported；notifications
  没有 XCTest reset resource，且本轮接入方没有请求入口，只承诺 runner 可处理已经出现且身份匹配的弹窗，
  不计作端到端已验证。runner 只验证英语、简体中文和繁体中文，其他设备语言不发布 decision capability。
  XCTest reset 会终止真机 App；0.4.0 允许重新运行接入方官方 run/attach 工具，不承诺 launcher 自动建立新
  debug isolate；exercise 处理弹窗后的同实例恢复仍须通过。
- **不放宽的部分**：必须显式指定 debug/test App、设备和签名产物；permission 身份或 decision 控件不唯一
  时 fail-closed；禁止坐标、截图识别、私有 API、静默签名和自动修改接入方 Xcode 工程。Android OEM runner
  与五类 permission trace 事件仍按 SC-040-02 延期。
