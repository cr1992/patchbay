## 版本定位

0.6.0 的窄主题一句话：**收敛用户心智、声明式输出、内部状态机边界**。

它来自一份外部架构评审的结论，评审的核心判断是：0.5.0 已经是一个安全优先的 Flutter 自动化内核，
但产品表面还不像一个干净、容易理解的工具。这两句话不矛盾——内核的正确性由 0.4.x / 0.5.0 的边界
工作换来，而每一次边界收紧都会在表面留下一条解释：四套身份域、两条点击通道、按面各异的遮挡语义、
按命令各异的输出形状。单看每条都有理由，合起来就是用户必须先理解内部结构才会用。

因此 **0.6.0 不以加能力为目标，以把表面定稿为目标**。本版的完成判据不是"命令更多"，而是：

1. 同一件事只有一个入口——用户按任务选，不必先学会四套身份域；
2. 同一个事实只有一个投影真源——输出形状由 descriptor 声明，不在实现里各写一份；
3. 同一段流程只有一处状态真源——门、生命周期、invocation 状态不再散在多个执行点上。

**两步走策略**：0.6.0 的成熟形态就是 1.0 的候选。1.0 本身几乎零新功能，它只做一件事——**把 0.6.0
定稿的表面转为长期承诺**（公共命令入口、稳定 JSON 字段、拒绝码集合此后按兼容规则演进）。这条策略
决定了本版的取舍口径：凡是"会让 1.0 之后仍需改动"的表面问题，本版解决；凡是"加了一个新能力、
表面因此多一块"的工作，本版不做。也正因为承诺在 1.0 才生效，0.6.0 仍是**可变表面**——不得把
1.0 的长期承诺提前写进 0.6.0 的对外文档。

表面收敛必然产生 breaking：入口收敛会改 CLI 命令面，投影声明化会改稳定 JSON。这不是本版的副作用而是
本版的内容，因此接入方迁移义务写进退出条件（见「验证与退出条件」的迁移义务条），不能等到发布前补。

### 主题核心候选一：任务导向命令入口

**现状事实。** 写类 UI 操作目前分布在四条路径上，各自锚在不同的身份上：`ui text set|enter <id> <gen>`
锚在注册目标的 target `id`；`ui tap` / `ui action <identifier> <gen>` 锚在 Semantics `identifier`
（另有按 `nodeId` 的既有 semantics action 路径）；`ui gesture tap <identifier> <gen>` 锚在 identifier
并可带目标内相对比例偏移；`ui reveal <identifier>` 驱动滚动容器并返回 `reachability` 告诉调用方
下一步该走哪条通道。PB-050-09 已经把"这四套身份分别是什么"写进 help——但那降低的是**解释成本**，
没有降低**选择成本**：用户仍然要先理解内部结构，才知道自己该敲哪条命令。

**候选形态（待裁决）。** 让用户按任务选入口——操作注册目标 / 派发辅助功能动作 / 装成真实指针按下去 /
把目标滚出来——身份域成为入口的参数或可推断的实现细节，而不是前置知识。

**与主题的关系。** 这是"同一件事只有一个入口"，是本版三条主线里最直接面向用户心智的一条。

**硬约束。** 不新增身份域，也不新增与现有命令相邻的第五套命令（见「明确不进入 0.6.0」）。入口工作
必须是**收敛**：新入口出现就必须同时给出旧路径的废弃或迁移窗口结论，否则它只是第五套。

**推荐分级：P0（本版主题的定义项）。** 理由：0.6.0 的定位就是表面定稿，这条不做则版本没有主题；
它同时决定 help、Skill 任务路由和 `INSTALL -> SKILL -> ...` 渐进式披露链的形状，必须先于其余表面工作
落地，否则后面每一项都要为一个还会变的入口做适配。

**必须先答的问题。**

- 入口是新增 CLI 层的任务动词（改 CLI 命令面，不动 wire），还是保留现有命令、只重排 help / Skill 的
  任务路由（零命令面变更）？前者是 breaking 但真正收敛，后者不 breaking 但心智负担只被移动一层。
- 是否允许一条入口在身份域之间自动回退（例如语义面失败自动改走指针面）？**推荐否**——评审的
  克制清单里"不做自动重连 / 自动换 session"背后的原则是"不静默换掉调用方以为在用的那条路"，
  自动换身份域是同一类问题：会让"命令说成功"与"实际走的通道"脱钩，也会让遮挡与门的语义
  变成运行期才知道的东西。
- 旧路径的窗口：本版即删、保留一版并告警、还是保留至 1.0？这条必须逐路径给结论，不允许"以后再说"。
- 需 Proposal：改公共命令 descriptor / CLI 公共面属[规划与交付治理](../planning.md)「必须写 Proposal」的
  第一条。

### 主题核心候选二：descriptor 驱动的声明式输出投影

**编号说明。** 仓主口径中的 PB-050-40。本分支 base 上 `docs/backlog.d/` 现有最大编号是 PB-050-35，
本条尚未登记；若并行分支已经登记，裁决时按其碎片内容回填编号。

**现状事实。** 0.5.0 范围内有两套"输出形状可以不止一种"的机制（PB-050-21 / PB-050-20，随 0.5.0 交付）：
`--view brief` 是 opt-in 瘦 JSON，字段清单由 [brief 视图 Proposal](../proposals/0.5.0/brief-view.md) 冻结
并以 golden 锁定；树类大载荷超阈值落 artifact、stdout 只返回校验路径。两者都证明形状可以分层，但
**每一层的字段选择仍然写在实现里**，descriptor 不知道自己的命令有几种投影。

**候选形态（待裁决）。** 让 descriptor 声明每条命令的输出投影，CLI 与 host 按声明投影，不各自维护
第二份字段清单。

**与主题的关系。** 这是"同一个事实只有一个投影真源"。它对 1.0 的价值最直接：投影一旦声明化，
稳定 JSON 的兼容边界就有了机检位置——1.0 之后"这个字段能不能改"可以由声明回答，而不是靠人读实现。

**推荐分级：P0 或 P1，取决于是否进 wire。** 若投影声明只落在 CLI 与 descriptor 的本地投影层（不进 wire），
建议 P1；若进 wire（老 host 上不可用、需要降级语义），它就与入口收敛同属本版定稿面，建议 P0。

**必须先答的问题。**

- 投影是否进 wire？进 wire 意味着老 host 拿不到声明、需要一条明确降级路径；不进 wire 则声明只对
  新旧 host 一致地在 CLI 侧生效，代价是 host 侧的人读摘要仍无真源。
- `--view brief` 的既有 golden 是否要求逐字节保持？推荐是——本版是表面定稿，不是表面翻新；brief 的
  字段集合若因声明化而漂移，接入方脚本会在没有任何 breaking 说明的情况下坏掉。
- 是否覆盖人读输出？人读摘要目前**不是**稳定契约；把它纳入声明等于把它变成契约，1.0 之后就不能
  随手改措辞了。推荐先只覆盖机器可读投影。
- 需 Proposal：改 descriptor 与稳定 JSON。

### 主题核心候选三：session 进程身份记录形态收尾

**base 事实（重要）。** 在本分支 base（`origin/dev/0.5.0`）上，PB-050-31 仍是 `target: —` / `待排期`，
`PlatformProcessUtils.processStartTimeSignature` 仍取 `ps -o lstart=` 的**本地时区**字符串、没有 scheme
前缀。仓主口径中"0.5.0 已修 TZ 缺陷并带 scheme"若已在并行分支落地，本条按落地后的残留改写；本稿因此
分两种情形给建议。

**情形 A：TZ 修复已随 0.5.0 交付（带 scheme 前缀的加法字段）。** 那么 0.6.0 的残留就不在探测层而在
**记录形态**：scheme 会随平台和实现继续增加，老 reader 靠"scheme 不同 = 无法验证，绝不判死"降级，
但降级路径每多一条，"这条记录到底能不能被验证"就越难回答；这正是本版"同一段流程只有一处状态真源"
主题的一个具体实例。同一个会话目录还被另外两条已登记的债读着——PB-050-19 的 `.quarantine` 隔离与
PB-050-29 的 doctor 路径输出。**推荐：把三者合成一个"会话记录形态"交付单元一起裁决**，分级 P1；
单独排任何一条都会重复一次持久化兼容评估。

**情形 B：TZ 修复未随 0.5.0 交付。** 那么 PB-050-31 本身就是 0.6.0 的候选，推荐 P1，且**必须先出
Proposal**：它是持久化字段的格式变更，碎片里已经写明 naive 实现会把新格式签名与升级前记录里的旧串
直接比对、全部判为不等，于是升级本身就删光所有活会话记录——正是这类 fail-closed 缺陷要防的事故。

**必须先答的问题。** 情形 A 下，记录目录是否需要显式版本化，还是继续靠字段级 scheme 前缀承载兼容；
以及三条债合批的边界是否成立（它们共享目录但不共享调用链，合批理由是"同一次兼容评估"，不是"同一段代码"）。

### 工程底座候选一：invocation 属性化状态模型

**编号说明。** 仓主口径中的 37，本分支 base 上尚未登记。

**现状事实。** 0.5.0 的 [invocation cancellation Proposal](../proposals/0.5.0/invocation-cancellation.md)
已经把"调用方不再等待"和"底层确实停了"分成两个事实，并把 registry/external 与 direct 统一到同一份
host admission 预算下；`docs/design.md` 的立场 1 和立场 6 也已经把受理、执行与 job 终态的词表钉死。
剩下的问题是**表示形式**：这些事实目前分散成 host invoker、job ledger 与 dispatcher 里的若干布尔位、
时间戳与容量计数，读的人要跨三处才能回答"这条 invocation 现在处于什么状态"。

**候选形态（待裁决）。** 把它们收成一个显式的属性化状态对象，让状态迁移可以单独读、单独测、单独失败。

**与主题的关系。** "内部状态机边界"这条的主体。注意它是**内部**——它的价值在可维护性和 1.0 之后的
可演进性，不在对外能力。

**推荐分级：P1，且以"零对外语义变更"为前置条件。** 理由：只要它改变任何对外可观察终态、退出码或
资源上限，它就不再是底座重构而是新契约，那就必须走 Proposal 并重新排优先级——而新契约与本版
"不以加能力为目标"的定位冲突。

**必须先答的问题。** 是否接受"零对外语义变更"作为硬约束（推荐接受）；若接受，它可按
[规划与交付治理](../planning.md)「不改变外部行为的重构无需 Proposal」条走，只需在 MR 里写清契约与
验收；若不接受，先出 Proposal 再谈分级。

### 工程底座候选二：超级 bridge 按状态机阶段拆分

**编号说明。** 仓主口径中的 38，本分支 base 上尚未登记。

**现状事实（与已有结论的冲突点，裁决前必读）。** [源码结构规范](../code-structure.md)的「当前已知待拆项」
已经逐个读过结构并给出判断：**应当拆分**的是 `walkUiManifest`（531 行）、`launcher.dart` 的 `run`
（360 行）、`friendly_command_registry.dart` 的 `resolve`（310 行）三个函数——它们命中"一个函数串起
多个可命名阶段"；而 `semantics_bridge` / `gesture_bridge` / `manifest_parser` / `artifact_service` /
`trace_store` / `doctor_checks` / `release_checker` 这些**因文件长度**被点名的对象已经复核为
**维持现状**（长度来自同构成员集合与内聚类，属"不该拆分"）。所以"超级 bridge 拆分"这个说法必须
先落到具体函数上，否则它与已有复核结论直接冲突。

**候选形态（推荐）。** 把范围钉在两类：一是 code-structure 已判定"应当拆分"的三项；二是本版范围内
改动实际触及、并新命中警戒线的函数。**不做横切重写**——0.5.0 的"不为压结构告警横切重写 CLI"应
继续有效。

**推荐分级：P1。** 理由：它是纯内部重构、行为零漂移、可按函数逐个回退，且不占裁决预算；同时它是
1.0 之前最后一次成本较低的结构整理窗口。

**必须先答的问题。** 范围是否按上面两类钉死；是否要求每次拆分附行为零漂移证据（推荐要求：拆分前后
测试清单可对账，沿用 0.4.1 的 PB-041-06 先例）。

### 工程底座候选三：gate 声明 / 执行真源统一边界

**编号说明。** 仓主口径中的 39，本分支 base 上尚未登记。

**现状事实。** `docs/design.md` 立场 3 是"门是声明的，不是散落的"，但**执行**目前分布在至少四处：
已接受的 [domain gate 强制执行 Proposal](../proposals/0.5.0/domain-gate-enforcement.md) 把 `plane: domain`
的 `gates` 从 catalog-only 升为 dispatch-enforced（PB-050-25，随 0.5.0 交付）；`ui.reveal` 另有"每步派发前重评门"的专用三层预算
（[scroll-reveal Proposal](../proposals/0.5.0/semantics-scroll-reveal.md)）；gesture 面另有接入方注入的
gesture policy（`reachability: pointer` 不等于手势会被放行，见 [guide](../guide.md) 的分流说明）；
semantics action 面另有 `PatchbaySemanticsActionPolicy`。声明在一处，执行在四处。

**候选形态（待裁决）。** 给"声明的门在哪里被执行"建立一条真源边界，让每一类门都能回答：谁声明、
在哪一步评估、拒绝形状是什么、老 consumer 上如何降级。

**与主题的关系。** "同一段流程只有一处状态真源"的安全侧。它也是入口收敛的前提之一——用户按任务
选入口的前提是"同一任务在不同入口下的安全语义可解释"。

**推荐分级：P0 或 P1，取决于是否改变接入方注入形态。** 若统一只是把评估点收敛、拒绝形状对齐（不动
注入 API），推荐 P1；若要求 gesture policy 之类的运行时注入对象也声明化，那是接入方 breaking，
应与入口收敛同属 P0 定稿面。

**必须先答的问题。** 统一面覆盖哪几类门（descriptor 声明门 / 不可省略的基础门 / gesture policy /
semantics action policy / reveal 每步重评）；是否改变接入方注入形态；老 consumer 兼容语义。需 Proposal
（安全边界 + 兼容语义，两条都命中）。

### 既有登记条目的分级建议

以下六条已在 backlog 登记、`target` 均为 `—`。逐条给推荐分级或"继续待排期"的理由。

- **PB-050-29（doctor 的 `quarantinedFiles` 直接输出本机绝对路径）——推荐 P1。**
  它是"同一条脱敏原则目前唯一未套用的例外"，收敛它正是本版表面一致性主题的小件；碎片自己已把三种
  处置写清（维持现状并补一句解释 / 改相对路径 / 套用同款绝对路径脱敏），裁决成本低、实现小、
  可独立回退。若采纳「会话记录形态」合批建议，它与 PB-050-19、PB-050-31 后续同批更完整。

- **PB-050-30（snapshot single-flight 缺 host 侧主动放弃阈值）——推荐继续待排期。**
  除非 0.5.0 的 RC 或接入方验收出现过真实的挂死 provider 实例。理由：碎片明确它要重开
  [snapshot 资源与 revision Proposal](../proposals/0.5.0/snapshot-resources-revisions.md) 已裁决范围之外的
  方向（摘除重开 vs 悬空 provider 调用与乱序 settle 的 trade-off），属于"新增资源上限与取消语义"的
  重量级裁决；把一条 host 内部可靠性方向塞进一个表面定稿版本，会直接冲掉"不以加能力为目标"的定位。
  若仍要排入，前置是先修订该 Proposal，不能照搬当前"只在 settle 时清除"的实现。

- **PB-050-33（候选分支的接入方可验性：包间互引是 hosted 形态）——推荐 P1，但按发布流程债排。**
  理由：0.5.0 的两个接入方验收已经实证过这条成本，而 0.6.0 是表面 breaking 版本、候选期的接入方
  验收量只会更大——一个抬高每次验收成本的障碍，在这个版本里的边际代价最高。碎片给的两条路
  （候选期发 prerelease 供直接声明版本号验收 / 在接入文档写明四包整组 `dependency_overrides` 配方）
  都不动运行时，可与代码交付完全并行。**待裁决：二选一还是都做**；若发 prerelease，还要裁决版本号
  形态以及是否写进[发版清单](../release-checklist.md)。

- **PB-050-34（遮挡准入在注册目标 text 面缺位的立场）——推荐先裁方向，再定分级。**
  这是六条里最"心智"的一条，也与主题核心候选一直接耦合：同一浮层遮挡下 `ui tap` 会按 DG-050-09 的
  遮挡准入拒绝，而对同一个被遮挡的注册文本目标执行 `ui text set` 返回 `applied` 且文本真的写进去了
  （实测见[目标面遮挡语义复现](../verification/0.5.0-target-plane-occlusion-repro.md)发现 1）。
  两个方向的分级不同：裁"注册目标面是接入方显式声明的自动化面、与装成用户的语义面刻意不同档"，
  则是纯文档明示，**P1 小件**；裁"应与语义面对齐"，则要动 `PatchbayUiTargetDescriptor` 状态模型并
  可能新增拒绝码，**需 Proposal**，且应与入口收敛同批——因为"用户按任务选入口"的前提正是同一任务在
  不同入口下的安全语义可解释。DG-050-09 已裁决的范围明确限定"点性 semantics 派发"，不覆盖本条。

- **PB-050-35（`ui.reveal` 对已挂载但被遮挡目标应有可分辨的拒绝形态）——推荐 P1，并与 PB-050-34
  合成一个裁决单元。** 理由：两条是同一个事实（遮挡）在不同面上的可见性差异；35 的事实在引擎内
  **已经可得**（reveal 引擎构造目标时已在读遮挡标志），而目前"目标被遮挡"与"目标压根不存在（含
  identifier 拼错）"返回同一个 `uiRevealNoScrollableContainer`，把调用方引导去查滚动容器和
  `--container`——真实业务里 modal 场景远比"目标不在列表里"常见，误导成本集中在排障时间上。
  实现前置：新增稳定 code 要过 error code 封闭注册表 ratchet（PB-050-23 已把它建起来）与对应
  Proposal；若 PB-050-34 裁"对齐"，35 几乎就是同一份 Proposal 的第二节。

- **PB-050-36——本分支 base 上不存在。** `docs/backlog.d/` 现有最大编号是 PB-050-35。需要仓主确认
  这是笔误、还是一条尚未登记 / 在并行分支上登记的条目；确认后本节补写。

## design gate 与 Proposal 闸门候选

本稿**不预分配 DG 编号**：编号一经分配不再改写，而并行分支可能正在登记新号。下列闸门在范围裁决时
由仓主分配 `DG-060-xx` 并建碎片。带"条件性"的闸门只在对应方向被裁到才需要。

- **闸门 A：任务导向命令入口。** 待裁决点：入口形态（新增任务动词 vs 零命令面变更的路由重排）；是否
  允许跨身份域自动回退（推荐否）；每条旧路径的废弃窗口结论；对 Skill 任务路由与渐进式披露链的影响。
- **闸门 B：descriptor 驱动的声明式输出投影。** 待裁决点：投影是否进 wire；老 host 降级语义；
  `--view brief` 既有 golden 是否逐字节保持（推荐是）；是否覆盖人读输出（推荐否）。
- **闸门 C：gate 声明 / 执行真源统一边界。** 待裁决点：统一面覆盖哪几类门；是否改变接入方注入形态；
  老 consumer 兼容与降级。
- **闸门 D（条件性）：注册目标 text 面遮挡立场（PB-050-34）。** 只有裁"与语义面对齐"才需要闸门；
  裁"刻意不同档"则是文档明示，无需 Proposal。
- **闸门 E（条件性）：`ui.reveal` 拒绝码分辨（PB-050-35）。** 新增稳定 code；若与 D 同批可并成一份。
- **闸门 F（条件性）：会话记录形态 / PB-050-31 后续。** 持久化格式与稳定 JSON，必走 Proposal。
- **闸门 G（条件性）：invocation 属性化状态模型。** 若接受"零对外语义变更"硬约束，可按重构走免
  Proposal 条款；一旦触及任何对外终态、退出码或资源上限，立即需要闸门。

裁决纪律沿用 0.5.0：Proposal 可以独立评审；实现 MR 不得夹带尚未接受的另一个 Proposal；需要共同底座时
先合底座。闸门 A / B / C 之间存在相互约束（见「依赖与实施顺序」），三者的裁决顺序本身是本版的串行点。

## 明确不进入 0.6.0

以下来自评审的克制清单与 0.5.0 继承条款，逐条都是本版的硬边界：

- **不做自动重连、自动换 session。** 沿用 0.5.0 对 PB-040-30 的处置：恢复体验不能静默换 peer，
  REPL reconnect 须先裁决固定 session、App/device identity、runtime replacement 与重试预算。
- **不把 `ui.reveal` 扩成通用导航。** 它维持"受限辅助能力"定位：只派发 scroll action、逐容器显式
  授权、不使用 `showOnScreen`、不合成指针滚动、不引入全树打分启发式、步数与预算有界。DG-050-10
  已裁决的边界不在本版重开。
- **不新增身份域，也不新增与现有命令相邻的第五套命令。** 表面工作只允许**收敛**：任何新入口都必须
  同时给出旧路径的迁移或废弃结论，"再加一个更好的入口"是本版明确的失败模式。
- **不引入黑盒驱动、网络采集、回放、恢复产品面**（PB-040-24 / PB-040-28 / PB-040-30 至 PB-040-37），
  也不引入外部一体化 E2E 平台的常驻 Supervisor/worker、case/suite DSL、Element 自动发现或结构模糊
  selector。
- **不为填满版本追加计划外命令或平台能力**（继承 0.5.0 的 P2 口径）。
- **不把 1.0 的长期承诺提前写进 0.6.0 的对外文档。** 0.6.0 仍是可变表面；承诺在 1.0 生效，提前写
  等于在还会改的东西上背书。
- **不为压结构告警横切重写 CLI**（继承 0.5.0）。结构工作按 [code-structure](../code-structure.md) 的
  已复核结论逐案推进，不按行数横扫。

## 依赖与实施顺序（草案）

1. **M0：版本基线。** 0.5.0 发布并回收 `dev/0.5.0` 后开建 `dev/0.6.0`；把 0.5.0 的公共面冻结为本版的
   breaking diff 输入（两个 CLI library 的封闭清单、稳定 JSON golden、error code 封闭注册表、
   `--view brief` 字段 golden、结构基线、兼容语料）。M0 还要把 `tool/check_planning.dart` 的
   `_activeVersion` 切到 `0.6.0`——**切换必须与范围表填好同批**，否则双向对账立刻判红。
2. **M1：先裁决，后动手。** 闸门 A / B / C 在任何实现 MR 之前完成 Proposal 与裁决。三条主线互相约束：
   入口决定 help 与 Skill 路由，投影决定入口返回什么，gate 边界决定入口能不能自解释安全语义。任一条
   先落地都会让另外两条被迫适配一个既成事实——**这是本版的串行点，且它在裁决层而不在代码热点层**
   （与 0.5.0 的 M3→M5 不同，那是同一份 `host_invoker.dart` 的物理串行）。
3. **M2：入口收敛。** 按闸门 A 结论实现，并同步 help、`describe`、Skill 任务路由与 `INSTALL` 起步流程。
4. **M3：声明式投影。** 按闸门 B 结论实现。若裁"不进 wire"，M3 可与 M2 并行；若进 wire，须在 M2 之后，
   因为入口形态决定投影要覆盖哪些命令。
5. **M4：gate 真源边界。** 按闸门 C 结论实现。若涉及接入方注入形态变更，须在 RC 前留出接入方
   适配窗口。
6. **M5：工程底座。** invocation 属性化状态模型与结构拆分不阻塞 M2–M4，可全程并行；结构拆分按
   code-structure 已判定"应当拆分"的三项 + 范围内新命中警戒线的函数推进，逐函数独立回退。
7. **M6：小件批。** PB-050-29 / PB-050-32 / PB-050-33（以及裁到 P1 的 PB-050-34 / PB-050-35 与会话记录
   形态合批件）可随时插队，各自独立回退，不得为它们推迟已绿的主题主线。
8. **RC。** 冻结范围，只接发布阻断修复；固定候选 SHA 后跑完全部门禁与两条 example 预检、完成接入方
   真机验收，并保持至少 72 小时无 P0/P1 重开。任何代码变更都生成新候选并重计。

  没有执行位置。若仓主要它成为真门禁，需另立条目给 ratchet 增加基线阻断模式，见待裁决清单。）

## 回退边界（草案）

- 闸门 A / B / C 的实现各自独立回退。入口收敛回退只移除新入口与对应的 help / Skill 路由，**不回退旧
  路径**；投影声明化回退到实现内字段清单，`--view brief` 既有 golden 不变；gate 边界回退保留 0.5.0
  已交付的 domain 写命令 dispatch-enforced 语义（PB-050-25），不得连带回退。
- 小件（PB-050-29 / 32 / 33 与裁到 P1 的 34 / 35）各自独立回退。34 与 35 若合成一份 Proposal，实现仍
  应分 MR，使"文档明示立场"与"新增拒绝码"能分别回退。
- 结构拆分的回退单位是**单个函数的拆分 MR**，不是整个 M5；每次拆分必须行为零漂移，否则它不具备
  独立回退性。
- 沿用 0.5.0 规则：回退新增面时保留复现失败测试（标注 skip 理由），不得连同证据一起回退。
- 会话记录形态若合批交付，持久化格式变更与 doctor 输出脱敏应分 MR：前者有升级期兼容风险，后者没有。
